Notas sobre a configuração (verificadas na documentação e no código-fonte oficiais):

- O ID a usar no perfil é o `shortName` da inspeção (`ParametersPerMethod`); `MethodWithTooManyParameters` é apenas o ID usado para suprimir o aviso.
- O formato do perfil YAML tem as chaves na raiz (`baseProfile`, `inspections`), e não `profile: base: name:` como no Listing 3 do guião.
- `pr-mode: false`: o Qodana analisa sempre o projeto completo. Com o modo "só ficheiros alterados", num PR o Qodana analisa também o `main` para comparar e falha enquanto a configuração não existir no `main`.

## Limiar de partida

A Tabela 2 do guião (Tabela 2.2 do livro *Object-Oriented Metrics in Practice*) não inclui valores para o número de parâmetros. Usou-se como ponto de partida o perfil *Long Parameters List* do MetricsTree (NOPM ≥ 4, ou seja `m_limit = 3`) e, como valor final, o limite *Very-high* de NOPM do MetricsTree (5 parâmetros, ou seja `m_limit = 4`).

## Reflexão

Com o limiar final (`m_limit = 4`), a ferramenta não encontrou instâncias do cheiro no código do BattleShip2 e detetou corretamente o método provocado com 9 parâmetros. Há falsos negativos: o construtor `Ship(...)` (4 parâmetros) e o *record* `MoveDatabase.StoredShot` (6 componentes) nunca são assinalados, porque a inspeção ignora construtores e componentes de *records*; não se observaram falsos positivos. O resultado é muito sensível ao limiar: com `m_limit = 3` o gate falha por causa de `Game.printBoard` (4 parâmetros) e com 4 ou 5 passa, enquanto o `severityThresholds.any` só altera a tolerância do gate (com `any = 1` o mesmo problema é detetado, mas o gate passa). Ao contrário das estratégias do livro, que usam limiares relativos (média e desvio-padrão de um conjunto de sistemas) e combinam várias métricas com condições lógicas, o Qodana aplica um único limiar absoluto por inspeção, pelo que este gate é apenas uma aproximação.
